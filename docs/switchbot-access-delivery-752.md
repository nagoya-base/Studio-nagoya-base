## 2. 配送契約

### 2.1 宛先・差出人・件名・本文
- **宛先（正規の受渡し先）**: 予約台帳 `Bookings` の `email` 列（予約フォームの代表者メールアドレス）。**送信の直前にだけ**、`bookingId` が一意に一致した1行の `email` セルを読む（`AccessLedgerReader.readRecipient`）。通常の照合（`readFromSheet`）は従来どおり `email` 列を読まない。宛先は状態ストア・配送記録・ログ・通知に保存しない。
  - **特定できなければ送らない**: 0件・複数件・列欠落・列重複・複数宛先（`,` `;` 空白 `<>`）・不正形式はすべて「未送信確定」（`DELIVERY_RECIPIENT_UNRESOLVED`）。管理者へ引き継ぐ。
  - ※「予約の代表者メール＝正規の受渡し先」は設計上の前提。運営が別の受渡し先（例: 予約確認メールと別の連絡先）を定める場合は、`resolveRecipient` の差替えで対応する（要運営確認）。
- **差出人**: 独立GASの実行アカウント（MailApp）。表示名は設定 `delivery.senderName`。`replyTo` は任意（`delivery.replyTo`、運営が非公開設定で指定）。未指定なら `noReply`。
- **件名**: 初回 `【{施設名}】入室用の暗証番号のご案内`／変更・再発行 `【{施設名}】暗証番号のご案内（変更のお知らせ）`。
- **本文**（固定文面。`renderCodeMail`）: 暗証番号／ご利用可能な時間（JST）／対象施設と予約番号／【ご利用にあたって】（案内した時間内のみ利用可／利用する方以外には共有しない／お困りの際は問合せ。#785 で簡素化）／【お問い合わせ】に問合せ案内（`delivery.inquiryNote`）。「利用後はメールを削除」「漏洩の恐れの連絡と番号無効化の文言」は本文から外した（案内の簡素化であり、漏洩疑い時の管理者による失効・代替入室・本人/予約確認などの内部手順は維持する）。変更案内では「以前の暗証番号は使用できません」（旧キーの削除確認済みのときのみ。未確認なら断言しない）。
- **載せないもの**: 完全な端末ID、キーボックスの場所・番号、バックアップキー、手動コード、代替入室の手順。これらは必要な人にだけ、本人・予約確認を経て管理者が個別に案内する。
- **設定**（`ACCESS_CONFIG.delivery`。メールアドレスや番号は含めない）: `senderName` / `facilityLabel` / `inquiryNote` / `replyTo`（任意）/ `startHoursBeforeDay`（既定6）。不正なら `CONFIG_INVALID` で全ジョブを止める。

### 2.2 配送ID・永続状態
- 配送IDは `DLV-` + sha256(`発行OP id` | `D` | `配送連番`) 先頭16桁。**OP id は 予約ID:revision:Keypad:ISSUE#attempt** なので、改訂・再発行・発行操作ごとに別の配送になる。予約単位で固定しないため、初回配送済みでも変更後の新キーは再案内できる。一方、同じOP（同じ変更）の重複イベント・ジョブ再実行では同じ配送記録に当たり、再送されない。
- 配送記録は発行 record とは別の `DLV_<OP id>` に永続化（宛先・コード・本文は持たない）。

| 状態 | 意味 | 次 |
|---|---|---|
| `NOT_SENT` | 送信していないと確定（宛先未解決・送信枠切れ・送信前の検証失敗） | 上限（既定3回・10分間隔）まで同じ配送IDで再試行。上限到達で `DELIVERY_RETRY_EXHAUSTED` を管理者へ |
| `SENDING` | **外部送信の直前に永続化**。保存に失敗したら送信しない | 成功→`DELIVERED`／再開時にこの状態なら `UNKNOWN` |
| `DELIVERED` | 外部送信の成功を記録 | 再送しない。管理者判断の `REGUIDE` のみ |
| `UNKNOWN` | 送信したか断定できない | **自動再送しない**。管理者判断のみ（§4） |
| `SUPPRESSED` | 取消・旧改訂・期限切れ・対象変更・管理者の手動対応で打ち切り | 以後このコードをメールしない |

### 2.3 状態遷移
```
ISSUED_CONFIRMED（発行反映確認済み）
  └ 配送ジョブ（5分）→ 送信直前ゲート（§3）
       ├ 保留（18:00前・台帳読取失敗・支払/承認不明・OFF）… 何も送らず次回再評価
       ├ 打切り（取消・旧revision・期限切れ・対象/期間変更）… SUPPRESSED
       └ 通過 → DLV: NOT_SENT → SENDING（永続化） → 外部送信
                 ├ 成功 → DELIVERED
                 ├ 「未送信確定」の失敗 → NOT_SENT（再試行 / 上限で管理者通知）
                 └ それ以外の例外・保存失敗・中断 → UNKNOWN（管理者通知）
```

## 3. 送信直前の安全ゲート（サーバー側・fail closed）

`deliverCycle` はサイクルごとに**台帳を1回読み直し**（読めなければ何も送らず `LEDGER_READ_FAILED` を管理者へ）、各配送対象について次をすべて満たす場合のみ送る。前回取得のスナップショットは使わない。

1. `ACCESS_ENABLED=ON` かつ `deliveryConfigured===true` かつ配送設定が有効（OFF時は台帳も読まない）。
2. OP が `ISSUED_CONFIRMED`（`UNKNOWN`/`FAILED` は対象外）で、予約索引の最新 head と revision・期間・Keypad が一致（コア）。
3. 台帳の最新レコードが一意に存在し、`FREEZE` 条件（支払/承認不明・追加料金未了・要復旧・時刻不正）に当たらない → 当たれば**保留**（解消後に再評価）。
4. 最新 revision が OP の revision と一致、`CONFIRMED`、`evaluateEligibility` が適格、期間・Keypad が OP と一致、有効期限前 → 満たさなければ**打切り**（`STALE_REVISION`/`CANCELLED`/`NOT_CONFIRMED`/`EXPIRED`/`TARGET_CHANGED` ほか）。
5. 利用日の `startHoursBeforeDay` 時間前（既定: 前日18:00 JST）以降 → 前なら**保留**（`NOT_YET`）。
6. 秘密（パスコード）が秘密ストアにあり形式が正しい。

> 残存リスク: ゲート通過〜MailApp 送信の数ミリ秒〜数秒の間に台帳が更新される競合は、台帳側の更新を単一ロックで排除できないため理論上残る。この場合でも、送られるのは「その時点で発行確認済みだった旧コード」で、直後の同期で旧キーは削除され使えなくなる（旧コードの再送はしない）。

## 4. 結果不明（PR #749 の「外部送信 → deliveredAtSec 保存」間の障害）の扱い

- **送信前に `SENDING` を永続化**し、成功後に `DELIVERED` を保存する。両者の間（外部送信成功→記録失敗、実行時間切れ、クラッシュ）で止まった場合、次回は `SENDING` が残るので **`UNKNOWN`** にして管理者へ通知し、**再送しない**。
- 送信手段の例外のうち、`error.notSent===true`（日次送信枠切れ、宛先未解決、文面生成の検証失敗）だけを「送信していない」と確定して再試行する。**MailApp の一般的な例外・応答喪失は未送信と断定できないので `UNKNOWN`**。
- 管理者判断（`accessAdminResolveDelivery(recId, decision)`。フラグOFFでも使用可、許可リストの管理者のみ、監査ログに操作者ラベルを記録、メールは送らない）:
  - `CONFIRM_DELIVERED` … 送信記録・受信確認を管理者が確認した → `DELIVERED`（再送しない）。
  - `ALLOW_RESEND` … 管理者が「届いていない」と判断（`UNKNOWN`/上限到達の `NOT_SENT`）→ **配送連番+1・新しい配送ID**で再送を許可。再送は次回の配送ジョブが§3の全ゲートを通して行う。
  - `REGUIDE` … `DELIVERED` だが利用者から未着の申出（本人・予約確認後）→ 上限付き（既定2回）で再案内。
  - `GIVE_UP` … 手動の代替入室で対応する → `SUPPRESSED`。
  - 再送系は、最新予約・発行確認済みキーと一致するときだけ許可（取消・旧revisionでは `NOT_CURRENT`）。
- 「一度限り送信」の保証はしない（MailApp は exactly-once ではない）。保証するのは「**無条件の自動再送をしない**」「再送は配送IDの連番と管理者判断を必ず伴う」こと。

## 5. 失敗の分離
- 配送失敗は `ISSUED_CONFIRMED` のキー・予約・決済・返金を変更しない。配送失敗を「入室案内完了」とみなさない（`deliveredAtSec` は成功時のみ）。
- 管理者通知は固定分類（コード・予約ID・revision・端末末尾4桁・状態のみ）。`DELIVER_FAILED` / `DELIVERY_UNKNOWN` / `DELIVERY_RETRY_EXHAUSTED` / `CHANGE_CODE_UNDELIVERED` / `DELIVERY_RECIPIENT_UNRESOLVED` / `DELIVERY_NOT_CONFIGURED`。同一 record×コードは重複抑止、通知失敗は次回再通知。
- 既存の予約・Stripe決済・返金・他ブランドのメールは変更していない。受渡し先を識別できない場合は送らず管理者へ引き継ぐ。

## 6. 変更・延長・取消との競合

- **変更後の再案内**: 変更後の新キーは新しい OP（revision）なので、旧キーの削除確認 → 新キーの発行・反映確認 → 新しい配送ID で別メールを送る（変更案内の文面）。旧OPが削除済みなら「以前の暗証番号は使用できません」を案内。旧キーが未確定（UNKNOWN）の間は新キーを発行しない（コアの既存規則）ため、新コードの案内もされない。
- **旧コードは送らない**: 配送待ち／再試行待ちの旧OPは、変更・取消で `ISSUED_CONFIRMED` でなくなる、または §3 の最新 revision 照合に失敗するため送られない（管理者の再送許可でも同様）。
- **延長承認と新コード利用可能は別**: 新コードの配送が `UNKNOWN`／未送達のとき、管理者へ `CHANGE_CODE_UNDELIVERED` を通知（入室中・期限直前は優先して代替入室）。利用者へは「利用可能」と案内しない。
- **同番号継続**は #756 の実機検証後に確定する。成立した場合は「延長後の有効時間の通知要否」を、本設計の文面（有効時間の表示）を流用して別途決める。
- **延長締切（終了1時間前）**・追加決済・予約間30分・施行日時ゲート（#758）は発行側（#753）の条件。配送は新コードを作らず、締切後に承認されなかった変更の旧コードを送らない（最新 revision 不一致で打切り）。Booking Admin の予約変更処理は重複実装していない。
- **漏洩時の失効**: 管理者が `accessAdminDelete(recId)` で個別失効。以後その OP は `ISSUED_CONFIRMED` でなくなり、メールもされない。新しい番号が必要な場合は予約の再同期（revision更新）または代替入室を管理者が選ぶ（自動の再発行はしない）。

## 7. 利用者案内・秘密の扱い
- 暗証番号は、利用者メール本文と秘密ストア（User Properties の `SECRET_*`）にのみ存在する。状態ストア・配送記録・通知・管理者ログ・棚卸し（`inventory` は配送状態のみ）・診断には出ない。
- 本文は「案内した時間内のみ利用可」「ご利用される方以外には共有しない」「お困りの際は問合せ」を明記（#785）。漏洩疑い時の失効・代替入室・本人/予約確認は、本文の記載に関わらず内部手順として維持する。
- 未着時: 利用者は問合せ案内（`delivery.inquiryNote`）に連絡 → 管理者が本人・予約を確認 → `REGUIDE` または代替入室を個別案内。
- 代替入室（手動解錠／手動パスコード発行／キーボックス内物理キー）の手順は運営手順書へ。バックアップキーの保管場所・キーボックス番号・手動コードは定型メール・通知・本書に書かない。

## 11. 暗証番号メールのHTML化（Issue #906）
- `renderCodeMail`（`gas/switchbot-access/SwitchBotAccessInfra.gs`）が `{ subject, body, htmlBody }` を返し、`sba_sendUserMail_` が `htmlBody` を `MailApp.sendEmail` に渡す（HTML + text/plain のマルチパート）。**件名・本文text・宛先・送信元名・replyTo/noReply・送信枠切れの扱い・再送/重複防止・配送記録は変更なし。** 文言の正本は text 版（従来文面を維持）で、HTML は同内容を表示するだけ。
