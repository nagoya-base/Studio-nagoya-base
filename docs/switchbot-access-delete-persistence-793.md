# 37DD 試験キー削除後残存の原因調査（Issue #793 / #756 第1段階）

調査のみ。コード変更・実機API通信・Script Properties 変更・本番有効化は行っていない。公式仕様（SwitchBotAPI README・公式Issue）への**外部照会はこの環境では実施していない**。仕様の確認が必要な項目は「要確認」と明記し、断定しない。

## 0. 事実（Issue #793 の時系列。JST）

発行(11:34)・VERIFY_ISSUED(11:39, keyCount=2)・DELETE受理(11:41, `API_ACCEPTED_NO_COMMAND_ID`)・VERIFY_DELETED(11:46, `TEST_KEY_STILL_PRESENT`)・公式アプリでも11:52まで残存・11:54にオーナーが手動削除。発行・削除とも `commandId` なし。残存は**公式アプリにも約11分間**出ていた。

## 1. 原因候補の仕分け

### A. 実測（リポジトリ内の記録）で確認できたこと

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| 過去の成功実績 | #713 手動Actions（2026-11-03・別の検証キー）で `deleteKey` を `commandId` なしで1回送信 → その後 keyList が1件に復帰 | `docs/switchbot-passcode-verification-713.md` 73–74行 |
| commandId 不在は異常ではない | `createKey`/`deleteKey` とも `statusCode=100, body={}` で処理は反映された例あり。公式Issue #466 にも同型の報告 | 同 57行 |
| 今回との条件差 | 実績は**発行直後に近い短命キー**（有効10〜15分）。今回は有効1時間・発行から削除まで7分・削除前に VERIFY で keyList 読取済み | #713 / #791 docs |

### B. 実装差分（コード照合で判明。**原因とは未確定**）

| 項目 | #713（削除が反映された経路） | #791 試験GAS / 本番コア（残存した経路） |
| --- | --- | --- |
| エンドポイント | `POST /v1.1/devices/{deviceId}/commands` | 同一 |
| ペイロード形 | `{commandType:'command', command:'deleteKey', parameter:{id}}` | 同一 |
| **`parameter.id` の型** | keyList の値を**そのまま**送信（`resolvePasscodeIdByName` が `keys[0].id` を無加工で返し `buildDeleteKeyBody(id)` へ） | **`String(keyId)` に強制変換**（`SwitchBotAccessInfra.gs` 1657行、`SwitchBotAccessCore.gs` 476行、`SwitchBotAccessApp.gs` では無加工で転送） |
| 保存経路 | リレーの状態に保存 | User Properties `TESTKEY_ID` に `String(hits[0].id)` で保存 |

keyList の `id` が数値で返る場合、#713 は数値、今回は文字列を送っている。受理（`statusCode=100`）は型に依らず返る可能性があり、**受理されたのに実行されない**（型不一致で端末側が対象を特定できない等）ことは理論上ありうる。ただしこれは**推測**であり、keyList の `id` の実際の型を本調査では確認していない。

### C. 公式仕様に照らした要確認事項（未確認）

1. `deleteKey` の `parameter.id` の型（数値 / 文字列）と、不一致時の挙動。公式READMEの記載・例の確認が必要。
2. 受理（HTTP200 / `statusCode=100`）が意味する範囲（クラウド受付のみか、端末への反映完了か）。#733 で別API(Webhook)の `190` が「デバイス状態がサーバと非同期」と定義されていた点から、**クラウドと端末の同期ずれ**は一般的に起こりうる。
3. `commandId` が返らない条件。公式READMEのKeypad例には `commandId` があるが実機では返らない（#744）。
4. Webhook(`changeReport`/`deleteKey`)で実行結果が取れるか。`commandId` なしのため相関できず、今回の経路では**実行結果を確認する手段が keyList のみ**。
5. 公式アプリの一覧表示が keyList と同じサーバデータ由来か（キャッシュ/同期の仕組み）。

### D. 推測（検証不能・現時点で支持も否定もしない）

- 端末側（Keypad）への反映遅延・端末オフライン・BLE/ハブ経由の同期失敗。ただし「公式アプリで約11分後も残存」はクラウド側にも未反映だったことを示すため、単なる短時間遅延とは決めつけない。
- 削除受付後の実行失敗（権限・対象IDの不一致・同期失敗）。
- 発行から読取までの間に端末の状態が keyList に正しく反映されていなかった可能性。

## 2. 現行実装の安全点検（予約本番側）

| 点検項目 | 現状 | 判定 |
| --- | --- | --- |
| 「API受理」を削除成功扱いにしないか | 本番コアは `DELETE_SENT` → keyList で ID・名前の**両不在**を確認して初めて `DELETED_CONFIRMED`。残存のまま上限なら `KEY_REMAINS` で `UNKNOWN`＋通知。試験GASも `TEST_KEY_STILL_PRESENT` で停止 | 適切 |
| 自動再送 | なし（試験GAS・本番コアとも） | 適切 |
| 通知 | `stopUnknown` が運営者通知を発行。通知失敗時は後続実行で再通知 | 適切 |
| 残存コードの解錠リスク | 今回の実機では、残存期間中に試験キーで解錠可能だったかは**未確認**。期限切れ（`endTime` 経過）後に解錠不可となる保証も未確認 | **要確認（最大のリスク）** |
| 読取窓 | `maxReads=3` / `readWaitSec=600` は、今回の事実（11分後も残存）と同程度。反映が遅い場合は `UNKNOWN`（安全停止）に倒れるので誤成功にはならない | 安全側。ただし運営者負荷は増える |
| 手動撤去 | `UNKNOWN` 時の手順は公式アプリで手動削除 | 運用手順の明文化が必要（改善Issue案2） |

結論: **「受理=成功」とは扱っておらず、誤って成功扱いにする経路は見当たらない。** 懸念は「削除が実際には効かないことがあり得る」ことと、その間・期限後の解錠可否が不明な点。

## 3. 改善Issue案（切り分け）

1. **deleteKey の `parameter.id` 型の整合**（優先）: 公式READMEで型を確認し、#713 で成功した形（keyList の値そのまま）に揃えるか判断する。試験GAS・本番コア・`App.gs` で型の扱いを統一し、テストに「keyList が数値idのとき数値のまま送る」ケースを追加。実機API通信を伴うため #756 で別GO。
2. **削除未反映時の運用手順**: `UNKNOWN`/`KEY_REMAINS` 時の運営者対応（公式アプリでの手動撤去、解錠可否の現地確認、記録項目）を `docs/switchbot-access-key-748.md` 系に追記。
3. **期限切れ後の解錠可否**の確認方法（別の安全な試験設計。本番では行わない）。
4. **公式仕様問い合わせ**（秘密なし）: `deleteKey` 受理後に公式アプリへ残存した事象・`commandId` が返らない条件・`id` の型。再現情報はこの文書の時系列のみ（deviceId・キー名・passcode ID は含めない）。

## 4. 次回の再試験条件（37DD限定・オーナー別GO。**この文書では実施しない**）

- 前提: 上記改善案1の実装・レビュー・デプロイ完了後に、#756 でオーナーが別途GOを出すこと。コード作成・マージ・ARMED設定をもってGOとしない。
- `ACCESS_TEST_KEY_STATE=STOPPED`（5/5済み）を**無断でリセットしない**。再試験はオーナー判断を #756 に記録した上で、状態を意図的に再初期化する手順を別途定める。
- 最少API回数: 現行の5回（list / createKey / list / deleteKey / list）を基本とし、削除後の確認読取を追加する場合は上限を明示して増やす（案: 削除後 list を最大2回、間隔5分以上、合計7回以内）。自動再送・自動削除はしない。
- 観測: 削除受理(T0)から T0+5分、T0+10分の2点で keyList を読み、並行して公式アプリでも目視（時刻のみ記録）。
- 成功判定: 試験キーの名前・ID が keyList から不在、かつ既存の通常キーの件数・指紋が不変、かつ公式アプリでも不在。
- 停止条件: 残存したまま上限に達したら即停止、`ACCESS_TEST_KEY_ARMED` を削除、オーナーが公式アプリで手動撤去。以後の追加API操作はしない。
- 安全条件: オーナー現地立会い、通常キー1件の保護、代替解錠手段あり、01FD・予約本番・第2段階への副作用ゼロ。解錠可否を確認する場合は有効期間と実施手順を事前に別途決める。
- 記録: Issue/PR/ログには時刻と固定結果コードのみ。完全deviceId・パスコード・Token/Secret・passcode ID・キー名は書かない。
