# 個別鍵の確認済み最終状態を Bookings 末尾1列へ保存する（Issue #971 Phase 1）

**正本は Issue #971 の本文。** 本書は実装メモで、PRのマージ・Bookingsの列追加（本番migration）・GASデプロイ・Script Properties設定・Phase 2（自動保存）を**許可するものではありません**。

## 1. 何をするか／しないか

- Access GAS の操作履歴が回収された後も、予約ごとの「**失効・不在を確認済み**」「**未発行を確認済み**」を運営アプリで確認できるようにする。
- 保存先は `Bookings` 末尾の **`accessKeyFinalStatus` 1列だけ**（`BookingsSchema.HEADERS_` の末尾追記）。予約別Script Properties・新DB・再試行キュー・カーソル・バッチAPIは作らない。
- **Access GAS（発行・削除ロジック・公開入口・OAuth権限）と Booking の予約・決済・鍵連携コードは変更しない。** 書込み者は、既に `spreadsheets` 権限を持つ運営GAS（`gas/ops-reservations`）の**管理者が明示実行する保存処理だけ**。
- 運営アプリの閲覧（一覧・詳細・`key_status`）は読み取り専用のまま。**画面を開いても書き込まない。** 自動トリガー・`script.scriptapp` スコープ追加・`ACCESS_ENABLED` の変更はしない（Phase 2は別承認）。

```
Access GAS（既存の鍵操作記録） ──既存の認証付きopsStatus（読取のみ）──▶ 運営GAS
   運営GAS: 管理者が opsSaveKeyFinalStatuses を実行 ─▶ 検証済みの結果だけ Bookings.accessKeyFinalStatus の1セルへ
   運営画面: Accessの現行記録を優先。Accessが正常に NONE のときだけ、保存値が現在の台帳と一致すれば補助表示
```

## 2. 保存値

`<CODE>@r<予約改訂番号>@h<16桁16進>`（例 `REVOKED_CONFIRMED@r3@h0123456789abcdef`）

| CODE | 意味 |
| --- | --- |
| `REVOKED_CONFIRMED` | 該当する鍵の失効・不在を記録で確認済み |
| `NOT_ISSUED_CONFIRMED` | 発行されていないことを操作記録で確認済み（取消・失効の予約で、全件が発行失敗のみ） |

- 空欄・履歴なし・読取失敗・不明は**保存しない＝判別不可**。「発行済み」「処理中」「期限切れ」「発行失敗」は最終確定結果に混ぜない。
- `@r` は保存時点の予約の改訂番号。`@h` は保存時点の台帳（予約ID・状態・ブランド・利用開始/終了・確定/取消/失効日時）の指紋（32bit FNV-1a×2）。**予約IDも指紋の入力に含める**（同じ改訂番号・同じ属性の別予約へ値が転記・行ずれで入っても有効としない。予約ID自体は保存しない）。**PIN・passcodeId・deviceId・氏名・メール等は含めない。**
- **現在の台帳の改訂番号と指紋が両方一致しなければ表示しない。** 改訂番号の増分は失敗してもログのみで予約処理を続ける設計（`bumpRevisionIfKeyRelevant_`）のため、「改訂番号は必ず進む」とは仮定せず、状態・日時が変われば指紋で無効になる。
- あくまで**保存時点の確認結果**で、SwitchBotの現在の状態を保証しない。

## 3. 保存してよい条件（`OpsKeyFinal.decide`）

すべて満たすときだけ保存する。1つでも欠ければ何も書かない。

- 対象ブランドは `snb` / `mens` / `studio_x`（正本 `AccessKeySnapshot.TARGET_BRANDS`。テストで一致を固定）。ブランドは問い合わせ候補の絞込みだけに使い、ブランドから鍵の状態は推定しない。
- Access が認証成功・`STABLE`・`record=FOUND`・履歴の切捨てなし・`opCount` と件数が一致・認識できない記録なし。**既存の照合（`OpsKeyStatus.evaluate`）の判定が保存コードと一致すること**（`MISMATCH` / `NEEDS_REVIEW` / 案内状態が認識できない記録などは保存しない）。
- **全改訂の発行操作**が `{DELETED_CONFIRMED, ALREADY_ABSENT, ARCHIVED_EXPIRED}`（失効・不在確認済み）か `FAILED`（取消・失効の予約のみ）。発行中・残存鍵・削除未確認・`UNKNOWN`・`ABANDONED`・失効確認前の `EXPIRED` が1件でもあれば不可。
- **取消・失効（`CANCELLED` / `EXPIRED`）**: 全件が `FAILED` → `NOT_ISSUED_CONFIRMED`。失効・不在確認済みを含み残りも確認済みまたは `FAILED` → `REVOKED_CONFIRMED`。
- **利用終了した `CONFIRMED`**: 現在の改訂の記録があり、**全件が失効・不在確認済み**で、**鍵の猶予込み有効期限（`validToSec`）も終了している**ときだけ `REVOKED_CONFIRMED`。Bookings の `endAt` の経過だけでは保存しない。全件が発行失敗のみの確定予約は保存しない。
- Access `NONE`・通信/認証エラー・`MISMATCH`/`NEEDS_REVIEW`・期限経過のみを根拠にした保存は禁止。
- **保存直前に台帳を再読込**し、予約ID・状態・改訂番号・指紋が同じで、重複・途中変更がないことを確認する。書込み後は同じセルを**読み戻して一致を確認**し、不一致は未保存として失敗にする。
- 既に**有効な保存値**がある予約は再問合せしない。保存値が古い（改訂・指紋の不一致）・形式不正のときは、現在の検証結果で置き換える。有効な別の値が見つかった場合は上書きせず衝突として数える。

## 4. 管理者の保存処理（Phase 1の運用）

1. 運営GASの Script Properties に固定設定 `OPS_KEY_FINAL_STATUS_WRITE` = `ON`（それ以外はすべて停止。既定は未設定＝OFF）。
2. 所有者本人が Apps Script エディタから `opsSaveKeyFinalStatuses` を実行（所有者認可は毎回）。1回の実行で問い合わせるのは**最大10件**（利用終了/取消から7日以内の対象ブランドの終端予約を、新しい順）。超過や、保存できない候補が先頭を占める場合は `deferred` 件数として返るので、次の順で再実行する: **まず通常の `opsSaveKeyFinalStatuses`（offset 0）を再実行**する（保存できた予約は候補から外れるため、後続の候補が前に詰まって届く）。**先頭の保存できない候補が固定されて `saved` が増えない場合にだけ**、`opsSaveKeyFinalStatusesNext10`（候補の11〜20件目）・`opsSaveKeyFinalStatusesNext20`（21〜30件目）へ進める（状態を持たない offset。0〜100の10の倍数のみ。保存が進むと候補が詰まるため、offsetを進めるときは直前の実行から候補が変わっていないことを `candidates` 件数で確認する）。**自動では繰り返さない。**
3. 戻り値・ログは件数と固定コードだけ（`candidates` / `offset` / `processed` / `saved` / `deferred` / `skipped`（理由別件数） / `stoppedBy`）。予約ID・保存値・行番号・URL・トークンは出さない。
4. Access の取得または書込みに失敗したら、その時点で停止し、失敗を成功扱いにしない。

**Phase 1の制約**: 管理者が実行しなければ保存されない。Access側で既に回収された履歴（例: 11月3日の予約）は**復元できず、空欄（判別不可）のまま**。今後も実行が間に合わなければ判別不可になる。**履歴の保全を保証するものではない**（ベストエフォート）。

## 5. 画面

- `key_status` の応答に `savedFinal`（`{code, label, source}` または `null`）を追加。**Accessが正常に `NONE`（接続成功・`STABLE`・記録なし）で、保存値が現在の台帳と一致し、台帳が終端（取消/失効、または確定で終了済み）のときだけ**返す。Accessに実記録がある・取得失敗・未接続・読取中の更新・索引不整合のときは `null`（Accessの結果を保存値で隠さない）。
- 画面は「**Bookings保存：過去の最終確認**」として、Accessの判定（履歴なし等）とは別ブロックで補助表示し、「保存時点の確認結果で、鍵の現在の状態を保証しない」旨を併記する。保存値そのもの（改訂番号・指紋）は画面へ渡さない。
- モック: `?key=saved`（`MOCK-002`）。

### 5.1 予約直後の表示（保存列は使わない・永続状態なし）

Accessが正常に `NONE`（接続成功・`STABLE`・記録なし）で、有効な保存結果もないときだけ、個別鍵の状態の主表示を「鍵の履歴なし（判別不可）」から予約状態による説明に置き換える（`OpsKeyFinal.scheduleView`。純粋な計算で、書込み・プロパティ・タイマーなし）。

| 予約の状況 | 表示 |
| --- | --- |
| 仮予約（`PENDING`） | 発行対象外（予約未確定） |
| 確定で、利用日の前日12:00 JSTより前 | 発行開始前 |
| 確定で、発行開始以降・利用終了前 | 発行記録なし（確認待ち）（未発行とは断定しない） |
| 取消・失効・利用終了後・時刻不正 | 説明なし（従来どおり「判別不可」。有効な保存結果があればそれを表示） |

- これは予約状態・発行予定時刻による説明で、**実鍵の不在を確認した結果ではない**。保存対象の `NOT_ISSUED_CONFIRMED`（実操作記録で確認済み）とは別のコード・別の表示。
- 優先順位: Accessの実記録 ＞ 検証済みの保存結果 ＞ 予約状態による説明 ＞ 判別不可。取得失敗・未接続・読取中の更新・索引不整合・矛盾は説明で覆い隠さない。
- モック: `?key=schedule`（`MOCK-002`）。

## 6. 本番導入（オーナーの明示判断後。自動マージ・自動デプロイ禁止）

1. 既存の列追加手順: `scope=admin-only` → 管理者が `migrateBookingsSchema` を実行（列名・追加数だけ確認）→ `scope=full, schema_migrated=true`。**手動でシートに列を挿入しない。** 末尾追記のみのため、旧コードは余分な列を無視して動く。
2. 運営アプリ（運営GAS）を別途更新。設定OFFのまま、一覧・詳細・鍵状態が従来どおりであることを確認。
3. 架空データと最小限の実予約で、保存と表示を確認してから `OPS_KEY_FINAL_STATUS_WRITE=ON`。
4. **緊急停止**: `OPS_KEY_FINAL_STATUS_WRITE` を削除（または `ON` 以外）→ 保存は即停止（画面表示は保存済みの値を読むだけで無害）。**ロールバック**: 運営GASを前の版へ戻す。追加した列は残して無害（旧コードは無視）。保存した値だけを消す場合は、管理者がセルを空にする（空欄＝記録なし）。

## 7. 180日個人情報整理（#680）との整合

- 保存値は非個人の状態コード＋整数＋指紋で、予約ID行に結び付く。行の `status` 等と同じく、**行が残る限り残る**。`PersonalDataRetention` の対象列・方針バージョンは変更しない。保持期間を延ばさず、個人情報も増やさない（テストで `PersonalDataRetention.gs` が新列を参照しないことを確認）。
- 「個人情報になり得ない」とは断定しない。予約IDに結び付く情報として、本人限定の運営アプリ経路（所有者認可済みの `key_status`）以外へは出さない。
