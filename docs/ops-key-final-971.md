# 個別鍵の確認済み最終状態を Bookings 末尾1列へ保存する（Issue #971 Phase 1）

**正本は Issue #971 の本文。** 本書は実装メモで、PRのマージ・Bookingsの列追加（本番migration）・GASデプロイ・Script Properties設定・Phase 2（自動保存）を**許可するものではありません**。

## 1. 何をするか／しないか

- Access GAS の操作履歴が回収された後も、予約ごとの「**失効・不在を確認済み**」「**未発行を確認済み**」を運営アプリで確認できるようにする。
- 保存先は `Bookings` 末尾の **`accessKeyFinalStatus` 1列だけ**（`BookingsSchema.HEADERS_` の末尾追記）。予約別Script Properties・新DB・再試行キュー・カーソル・バッチAPIは作らない。
- **Access GAS（発行・削除ロジック・公開入口・OAuth権限）と Booking の予約・決済・鍵連携コードは変更しない。** 書込み者は、既に `spreadsheets` 権限を持つ運営GAS（`gas/ops-reservations`）の**管理者が明示実行する保存処理だけ**。
- 運営アプリの閲覧（一覧・詳細・`key_status`）は読み取り専用のまま。**画面を開いても書き込まない。** 自動トリガー・`script.scriptapp` スコープ追加・`ACCESS_ENABLED` の変更はしない（Phase 2は別承認）。

```
Access GAS（既存の鍵操作記録） ──既存の認証付きopsStatus（読取のみ）──▶ 運営GAS
   運営GAS: 管理者が opsSaveKeyFinalStatuses を実行 ─▶ 検証済みの結果だけ Bookings.accessKeyFinalStatus の1セルへ
   運営画面: Accessの現行記録を優先。Accessが正常に NONE のときだけ、保存値が現在の台帳と一致すれば補助表示
```

## 2. 保存値

`<CODE>@r<予約改訂番号>@h<16桁16進>`（例 `REVOKED_CONFIRMED@r3@h0123456789abcdef`）

| CODE | 意味 |
| --- | --- |
| `REVOKED_CONFIRMED` | 該当する鍵の失効・不在を記録で確認済み |
| `NOT_ISSUED_CONFIRMED` | 発行されていないことを操作記録で確認済み（取消・失効の予約で、全件が発行失敗のみ） |

- 空欄・履歴なし・読取失敗・不明は**保存しない＝判別不可**。「発行済み」「処理中」「期限切れ」「発行失敗」は最終確定結果に混ぜない。
- `@r` は保存時点の予約の改訂番号。`@h` は保存時点の台帳（予約ID・状態・ブランド・利用開始/終了・確定/取消/失効日時）の指紋（32bit FNV-1a×2）。**予約IDも指紋の入力に含める**（同じ改訂番号・同じ属性の別予約へ値が転記・行ずれで入っても有効としない。予約ID自体は保存しない）。**PIN・passcodeId・deviceId・氏名・メール等は含めない。**
- **現在の台帳の改訂番号と指紋が両方一致しなければ表示しない。** 改訂番号の増分は失敗してもログのみで予約処理を続ける設計（`bumpRevisionIfKeyRelevant_`）のため、「改訂番号は必ず進む」とは仮定せず、状態・日時が変われば指紋で無効になる。
- あくまで**保存時点の確認結果**で、SwitchBotの現在の状態を保証しない。

## 3. 保存してよい条件（`OpsKeyFinal.decide`）

すべて満たすときだけ保存する。1つでも欠ければ何も書かない。

- 対象ブランドは `snb` / `mens` / `studio_x`（正本 `AccessKeySnapshot.TARGET_BRANDS`。テストで一致を固定）。ブランドは問い合わせ候補の絞込みだけに使い、ブランドから鍵の状態は推定しない。
- Access が認証成功・`STABLE`・`record=FOUND`・履歴の切捨てなし・`opCount` と件数が一致・認識できない記録なし。**既存の照合（`OpsKeyStatus.evaluate`）の判定が保存コードと一致すること**（`MISMATCH` / `NEEDS_REVIEW` / 案内状態が認識できない記録などは保存しない）。
- **全改訂の発行操作**が `{DELETED_CONFIRMED, ALREADY_ABSENT, ARCHIVED_EXPIRED}`（失効・不在確認済み）か `FAILED`（取消・失効の予約のみ）。発行中・残存鍵・削除未確認・`UNKNOWN`・`ABANDONED`・失効確認前の `EXPIRED` が1件でもあれば不可。
- **取消・失効（`CANCELLED` / `EXPIRED`）**: 全件が `FAILED` → `NOT_ISSUED_CONFIRMED`。失効・不在確認済みを含み残りも確認済みまたは `FAILED` → `REVOKED_CONFIRMED`。
- **利用終了した `CONFIRMED`**: 現在の改訂の記録があり、**全件が失効・不在確認済み**で、**鍵の猶予込み有効期限（`validToSec`）も終了している**ときだけ `REVOKED_CONFIRMED`。Bookings の `endAt` の経過だけでは保存しない。全件が発行失敗のみの確定予約は保存しない。
- Access `NONE`・通信/認証エラー・`MISMATCH`/`NEEDS_REVIEW`・期限経過のみを根拠にした保存は禁止。
- **保存直前に台帳を再読込**し、予約ID・状態・改訂番号・指紋が同じで、重複・途中変更がないことを確認する。書込み後は同じセルを**読み戻して一致を確認**し、不一致は未保存として失敗にする。
- 既に**有効な保存値**がある予約は再問合せしない。保存値が古い（改訂・指紋の不一致）・形式不正のときは、現在の検証結果で置き換える。有効な別の値が見つかった場合は上書きせず衝突として数える。

## 4. 管理者の保存処理（Phase 1の運用）

1. 運営GASの Script Properties に固定設定 `OPS_KEY_FINAL_STATUS_WRITE` = `ON`（それ以外はすべて停止。既定は未設定＝OFF）。
2. 所有者本人が Apps Script エディタから `opsSaveKeyFinalStatuses` を実行（所有者認可は毎回）。1回の実行で問い合わせるのは**最大10件**（利用終了/取消から7日以内の対象ブランドの終端予約を、新しい順）。超過や、保存できない候補が先頭を占める場合は `deferred` 件数として返るので、次の順で再実行する: **まず通常の `opsSaveKeyFinalStatuses`（offset 0）を再実行**する（保存できた予約は候補から外れるため、後続の候補が前に詰まって届く）。**先頭の保存できない候補が固定されて `saved` が増えない場合にだけ**、`opsSaveKeyFinalStatusesNext10`（候補の11〜20件目）・`opsSaveKeyFinalStatusesNext20`（21〜30件目）へ進める（状態を持たない offset。0〜100の10の倍数のみ。保存が進むと候補が詰まるため、offsetを進めるときは直前の実行から候補が変わっていないことを `candidates` 件数で確認する）。**自動では繰り返さない。**
3. 戻り値・ログは件数と固定コードだけ（`candidates` / `offset` / `processed` / `saved` / `deferred` / `skipped`（理由別件数） / `stoppedBy`）。ログの `skipped=` は `固定コード:件数` をコード昇順（最大20種類）で並べる。予約ID・保存値・行番号・URL・トークンは出さない。
4. Access の取得または書込みに失敗したら、その時点で停止し、失敗を成功扱いにしない。

**Phase 1の制約**: 管理者が実行しなければ保存されない。Access側で既に回収された履歴（例: 11月3日の予約）は**復元できず、空欄（判別不可）のまま**。今後も実行が間に合わなければ判別不可になる。**履歴の保全を保証するものではない**（ベストエフォート）。

## 5. 画面

- `key_status` の応答に `savedFinal`（`{code, label, source}` または `null`）を追加。**Accessが正常に `NONE`（接続成功・`STABLE`・記録なし）で、保存値が現在の台帳と一致し、台帳が終端（取消/失効、または確定で終了済み）のときだけ**返す。Accessに実記録がある・取得失敗・未接続・読取中の更新・索引不整合のときは `null`（Accessの結果を保存値で隠さない）。
- 画面は「**Bookings保存：過去の最終確認**」として、Accessの判定（履歴なし等）とは別ブロックで補助表示し、「保存時点の確認結果で、鍵の現在の状態を保証しない」旨を併記する。保存値そのもの（改訂番号・指紋）は画面へ渡さない。
- モック: `?key=saved`（`MOCK-002`）。

### 5.1 予約直後の表示（保存列は使わない・永続状態なし）

Accessが正常に `NONE`（接続成功・`STABLE`・記録なし）で、有効な保存結果もないときだけ、個別鍵の状態の主表示を「鍵の履歴なし（判別不可）」から予約状態による説明に置き換える（`OpsKeyFinal.scheduleView`。純粋な計算で、書込み・プロパティ・タイマーなし）。

| 予約の状況 | 表示 |
| --- | --- |
| 仮予約（`PENDING`） | 発行対象外（予約未確定） |
| 確定で、利用日の前日12:00 JSTより前 | 発行開始前 |
| 確定で、発行開始以降・利用終了前 | 発行記録なし（確認待ち）（未発行とは断定しない） |
| 取消・失効・利用終了後・時刻不正 | 説明なし（従来どおり「判別不可」。有効な保存結果があればそれを表示） |

- これは予約状態・発行予定時刻による説明で、**実鍵の不在を確認した結果ではない**。保存対象の `NOT_ISSUED_CONFIRMED`（実操作記録で確認済み）とは別のコード・別の表示。
- 優先順位: Accessの実記録 ＞ 検証済みの保存結果 ＞ 予約状態による説明 ＞ 判別不可。取得失敗・未接続・読取中の更新・索引不整合・矛盾は説明で覆い隠さない。
- モック: `?key=schedule`（`MOCK-002`）。

## 6. 本番導入（オーナーの明示判断後。自動マージ・自動デプロイ禁止）

1. 既存の列追加手順: `scope=admin-only` → 管理者が `migrateBookingsSchema` を実行（列名・追加数だけ確認）→ `scope=full, schema_migrated=true`。**手動でシートに列を挿入しない。** 末尾追記のみのため、旧コードは余分な列を無視して動く。
2. 運営アプリ（運営GAS）を別途更新。設定OFFのまま、一覧・詳細・鍵状態が従来どおりであることを確認。
3. 架空データと最小限の実予約で、保存と表示を確認してから `OPS_KEY_FINAL_STATUS_WRITE=ON`。
4. **緊急停止**: `OPS_KEY_FINAL_STATUS_WRITE` を削除（または `ON` 以外）→ 保存は即停止（画面表示は保存済みの値を読むだけで無害）。**ロールバック**: 運営GASを前の版へ戻す。追加した列は残して無害（旧コードは無視）。保存した値だけを消す場合は、管理者がセルを空にする（空欄＝記録なし）。

## 9. 保存0件の解釈（実測 2026-11-19 13:38 / 13:40）

**確認できた事実**: `candidates=11`、`processed` 合計11、`saved=0`、`deferred` 0、`stoppedBy` なし。つまり対象11件はすべて Access へ照会でき、いずれも `decide()` の保存条件（または保存直前の再検証）を満たさなかった。エラー停止ではない。

**確認できないこと**: 件ごとの理由。当時のログには `skipped`（固定理由コード別件数）が出ておらず、既存ログだけでは確定できない。以下は**原因候補**であり、断定しない。

| 候補（`skipped` の固定コード） | 起こり得る状況 |
| --- | --- |
| `NO_RECORD` | Access が `NONE`。終端後ほぼ1時間（`EARLY_PURGE_GRACE_SEC`）で回収されるため、手動実行が間に合わなかった予約。**保存はしない（`NONE` を根拠にしない）のが正しい動作**。対象期間は終了/取消から7日、Access の既定保持は3日のため、3日超の候補は原理的にこれになる |
| `KEY_VALIDITY_NOT_ENDED` | 鍵の猶予込み有効期限（`validToSec`）が未終了 |
| `ENDED_NOT_ALL_REVOKED` / `OP_NOT_SETTLED` | 利用終了後でも失効・不在の確認前、または発行失敗のみの確定予約（保存対象外の仕様） |
| `VERDICT_MISMATCH` / `REVISION_NOT_COVERED` ほか | 照合が要確認・不一致、現在の改訂の記録なし |

**修正要否**: 保存条件は変更しない（緩めない）。診断のため、上記の `skipped` 固定コード別件数を管理者手動実行のログに出す最小変更だけを行う（本PR。保存ロジック・プロパティ・トリガーは無変更）。次に手動実行する機会（追加のテストは不要）のログで、原因を分類できる。`NO_RECORD` が大半なら、Phase 1 の挙動は仕様どおりで、必要なのは Phase 2（回収前に間に合う頻度での保存）になる。7日の対象期間を3日へ縮める案は、ログで `NO_RECORD` の多さを確認してから別途判断する（問い合わせ枠の節約にはなるが、今回は変更しない）。

## 10. Phase 2 設計案（自動保存）

> 実装状況（2026-11-19）: §11 の入口 `opsSaveKeyFinalStatusesScheduled` を実装（本PR）。**トリガー登録・Ops GASデプロイ・設定変更はオーナーの判断後。**

**方針**: Phase 1 の `OpsKeyFinal.run`（検証済みの保存ロジック）をそのまま再利用し、**単一の時間主導トリガー1つ**から呼ぶ。予約別プロパティ・ID別カーソル/キュー/ハッシュ・新DB・新バッチAPI・Access側の変更・追加の監視基盤・新規権限は追加しない。画面・一覧・`key_status` は読取り専用のまま。履歴保存は**保証ではなくベストエフォート**。保存条件・既存の手動関数（`opsSaveKeyFinalStatuses` ほか）は変更しない。

1. **トリガーの作り方（第一案）**: オーナーが Apps Script エディタの「トリガー → トリガーを追加」で、時間主導トリガーを**一度だけ手動設定**する（15分ごと。削除も同じ画面）。**トリガー管理用コード（作成/削除関数・重複防止）も `script.scriptapp` スコープの追加も不要**（manifest・OAuth権限は変更なし）。プログラムでトリガーを作る案は今回は採らない。
2. **自動実行用の薄い入口**: 新関数 `opsSaveKeyFinalStatusesScheduled` を1つだけ追加し、`OpsKeyFinal.run`（offset 0）を呼ぶ。1回最大10件、新しい終端順（現行どおり）。
   - 設定 `OPS_KEY_FINAL_STATUS_WRITE` が `ON` 以外（`WRITE_DISABLED`）は**正常スキップ**（例外にしない・通信/読取/書込みなし）。
   - 結果が `ok:false`（認可・設定・台帳・ロック等）、または `ok:true` でも `stoppedBy` がある場合は、**固定コードだけの例外**（例: `Error('OPS_KEY_FINAL_SCHEDULED_FAILED:' + code)`。コードは `^[A-Z_\/0-9]{1,60}$` を満たす固定値のみ）に変換する。予約ID・保存値・行番号・URL・トークンは例外文に入れない。`BUSY`（手動実行と重なった）は次回再試行でよく、失敗扱いにしない。
   - 理由: Apps Script標準のトリガー失敗通知は**トリガー関数が例外で失敗したときだけ**送られる。`run` は `stoppedBy` を `ok:true` の結果として返し得るため、この入口で例外へ変換しないと通知されない。
3. **対象選択・再試行**: 現行どおり（終了/取消から7日以内・保存済みでない・終端を新しい順に先頭10件。状態を持たない）。15分ごとに同じ選択を再評価する。対象期間の変更・回転・キューは入れない。実データで取りこぼしの必要性が判明した場合のみ別Issueで扱う。
4. **トリガー実行時の認可**: 現行の認可は `Session.getActiveUser()` と `OPS_OWNER_EMAIL` の一致。時間主導トリガーでは `getActiveUser()` が空になり得るため、この入口だけ `Session.getEffectiveUser()`（トリガーを登録した所有者）と `OPS_OWNER_EMAIL` の一致を確認する（実装時にテストで固定）。
5. **停止・復旧**: 停止＝トリガー画面でトリガーを削除、または設定 `OPS_KEY_FINAL_STATUS_WRITE` を削除（`ON` 以外）。復旧＝トリガー再登録／設定ON。
6. **失敗の認知**: Apps Script標準の「失敗時の通知」（トリガー設定の通知頻度）を使う。メール送信スコープ・独自の監視は追加しない。画面表示は、開かない限り1時間以内に気付ける通知ではない。
7. **クォータ・実行時間（実測前の見込み）**: 最悪1実行 約25 fetch、96実行/日で約2,400 fetch/日（UrlFetch 20,000/日の約12%）。候補0件なら台帳読取のみ（約288 GET/日）。実行時間は初回の自動実行で実測する。
8. **受入**: Phase 1 の保存成功を事前に手動で作る必要はない。トリガー登録後、**初回の自然な終端予約**の自動実行ログ（`saved` / `skipped` / 失敗通知の有無）と、対象セルが `<CODE>@r<改訂>@h<指紋>` 形式か、他セルに変化がないかで確認する。
9. **残余リスク**: トリガー停止とAccessの早期回収が重なれば記録は失われ、その行は空欄（判別不可）のまま。既に回収済みの予約は復元できない。

**オーナー判断が必要な点**: (a) Phase 2の実装着手、(b) 15分間隔の時間主導トリガーを手動で一度登録すること、(c) 失敗通知にトリガー標準の失敗通知メールを使うこと。

## 11. Phase 2 自動保存の運用手順（`opsSaveKeyFinalStatusesScheduled`）

**実装範囲**: 運営GASに入口関数 `opsSaveKeyFinalStatusesScheduled`（引数なし）を1つ追加しただけ。保存処理は手動実行と同じ `OpsKeyFinal.run`（offset 0・1回最大10件・対象は終了/取消から7日以内・保存条件は無変更）。コードからトリガーは作らない・消さない。OAuthスコープ（manifest）・予約別プロパティ・キュー・Access/Booking側は無変更。**履歴保存の保証ではなくベストエフォート。**

**入口の動作**
| 状況 | 結果 |
| --- | --- |
| `OPS_KEY_FINAL_STATUS_WRITE` が `ON` 以外 | 認可・台帳・Accessに触れず即スキップ（正常終了） |
| 手動実行と重なった（`BUSY`） | 正常スキップ（次回の15分後に再試行） |
| 実行者が `OPS_OWNER_EMAIL` と不一致／空（`FORBIDDEN`/`UNAUTHENTICATED`）、台帳・Access設定の不備など `ok:false` | `OPS_KEY_FINAL_SCHEDULED_FAILED:<固定コード>` の例外 → 標準の失敗通知 |
| 実行できたが保存中に停止（`stoppedBy`） | 同上（固定コードのみ） |
| 保存0件・`skipped` が多いだけ | 正常終了（ログに件数と `skipped=CODE:件数`） |

例外文・ログには予約ID・氏名・保存値・行番号・URL・トークン・API生応答を含めない。トリガー実行では `Session.getActiveUser()` が空になり得るため、**この入口だけ** `Session.getEffectiveUser()`（トリガーを登録した所有者）を `OPS_OWNER_EMAIL` と照合する。画面・手動実行の認証は変更しない。

**オーナーが行う手順（マージ・Ops GASデプロイ後に1回だけ）**
1. Ops GAS更新workflowで本PRの内容を反映（`OPS_KEY_FINAL_STATUS_WRITE` は現状の `ON` を維持）。
2. 運営GASのApps Script編集画面 → 左の「トリガー」 → 「トリガーを追加」。
3. 実行する関数：`opsSaveKeyFinalStatusesScheduled`／イベントのソース：時間主導型／タイプ：分ベースのタイマー／間隔：15分おき。
4. 「エラー通知設定」は「今すぐ通知を受け取る」または「毎時」。保存。初回は所有者本人が認可画面を承認。
5. **トリガーは1本のみ**。2本以上作らない（重複しても `BUSY` で保護されるが、無駄な読取りになる）。

**受入確認（新しいテスト予約・手動実行の反復は不要）**: 自然に終端になった予約について、実行ログの `ops key_final_save DONE ... saved / skipped`、対象セルが `<CODE>@r<改訂>@h<指紋>` 形式か、他セルに変化がないか、失敗通知が来ていないかを見る。初回の自動実行で実行時間とクォータを実測する。

**停止・復旧**: 停止＝トリガー画面でトリガーを削除、または `OPS_KEY_FINAL_STATUS_WRITE` を削除（`ON` 以外）。復旧＝トリガー再登録／設定を `ON`。コードを戻す場合は `rollback_version`。

**残余リスク**: トリガー停止とAccessの早期回収（終端後最短約1時間）が重なれば記録は失われ、空欄（判別不可）のまま。既に回収済みの予約は復元できない。失敗通知メールは標準機能で、画面を開かなくても届くが即時性は保証されない。
