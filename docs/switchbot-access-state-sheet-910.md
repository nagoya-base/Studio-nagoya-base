# SwitchBot Access 状態管理のスプレッドシート化 評価（設計・調査 / Issue #910）

**正本は Issue #910。** 本書は設計・調査のみで、コード・設定・デプロイ・トリガー・`ACCESS_ENABLED`・OAuthスコープ・マイグレーションのいずれも**変更しません**（マージ＝本番反映ではない）。運営者が各段階を明示承認するまで、本番の鍵操作は現状のまま稼働を続けます。関連: #757（本番導入）、#887（状態保持・回収）、#906（鍵メールHTML）。

> 本書の件数・サイズは**コードの生成規則からの見積もり**です。この調査では本番GASを読んでいないため、実測値は §2.3 の読取専用手順で運営者が取得して #910 に固定コードの集計値だけ記録します。個人情報・秘密・予約ID・完全deviceId・暗証番号は本書にも Issue にも書きません。

## 0. 結論

| 項目 | 結論 |
| --- | --- |
| 推奨 | **案②（状態正本は Script Properties のまま維持＋運営者用の読取専用ミラーシート）を先に実施**。案①（監視・回収の改善）は②と同時に小さく入れる |
| 案③（正本をシートへ移行） | **今は着手しない。** ②の運用実績と実測値で §6 の判断条件を満たした場合だけ別Issueで再評価 |
| 50件超の問題 | GAS管理画面の**表示・編集の制限**であり、容量不足ではない。②で運営の可視性は解決する（Properties自体の件数は #887 のGCで頭打ち） |
| 本番への影響 | なし。移行を理由に `ACCESS_ENABLED` を OFF にしない・トリガーを止めない・既存OPを触らない |

理由: 鍵の二重発行・二重送信・削除漏れを防ぐ現行の状態遷移（`SENDING` を外部送信**前**に永続化、`UNKNOWN` は自動再送しない、単一 `LockService` 内で更新）は、`setProperty` が数ミリ秒で同期完了することに依存している。Sheets API（UrlFetch経由、1呼出しあたり数百ミリ秒〜秒、ネットワーク障害・クォータあり）へ正本を移すと、その前提が崩れ、**最悪ケース（外部送信は成功したが状態書込みが失敗）の頻度が上がる**。可視性の要望は読取専用ミラーで満たせる。

## 1. 現状（コードから確認できる事実）

- 状態ストア = `PropertiesService.getScriptProperties()`（`sba_stateStore_`。`ACCESS_` / `LEDGER_` / `BOOTSTRAP_` で始まる設定系は除外）。秘密（暗証番号）= `getUserProperties()` の `SECRET_<OP id>`（`sba_secretStore_`）。
- 公式上限: 1値 9KB、全体 500KB（`PROPERTIES_LIMITS`）。`storageStopRatio=0.7` で新規発行を止める（`STORAGE_NEAR_LIMIT`）。診断 `accessReadOnlyDiagnostics` が `store.keys / bytes / ratio / byPrefix / ops` を**値なし**で返す。
- 回収 = `accessDailyCleanupJob`（毎日00:15 JST近辺）→ `garbageCollect`（ロック保持下）。保持は #887 のとおり（§2.1）。未解決OP・必要な根拠は期限に関わらず保護。未知のキーは削除せず件数のみ報告。
- 台帳（Bookings）は別Spreadsheet。読取りのみ（Sheets API v4 の GET を `ScriptApp.getOAuthToken()` で呼ぶ）。マニフェストのスコープは `spreadsheets.readonly`（`SpreadsheetApp.openById` は `spreadsheets` が必要で使えないため REST を使用）。デプロイ検査は、リポジトリに**新スコープが増えるとリモートに無い限り `MANIFEST_NEW_OAUTH_SCOPE_REQUIRES_MANUAL_APPROVAL` で停止**する（`scripts/switchbot-access-gas-deploy-lib.js`）。
- Webサービス: `executeAs: USER_DEPLOYING`、`access: ANYONE_ANONYMOUS`。ロック失敗時のWebhook受信は `INBOX_` へ退避（TTL 900秒、`inboxMax` 上限）して取りこぼしを防ぐ。

### 2.2 件数・データ量の見積もり（未計測。生成規則からの概算）

1予約あたりの標準経路（発行→配送→削除、変更なし）で、概ね `OP×2 + BK + TRK + DLV + EVT×(2〜4) + ALERT×(0〜2)` ＝ **約8〜12キー**。変更が入るごとに発行＋削除でOPと関連キーが増える。したがって**予約が数件並ぶだけで50キーを超える**（GAS画面の表示制限に当たるのは容量不足ではなく件数）。未解決OPは期限なしで滞留するため、`unresolved` の件数が増加の主因になりうる（#887 の `estimateStorage` が同じ前提）。

総量の見積もりは `estimateStorage` の式（`bookingsPerMonth × 保持30日 × (1+変更) × 2 OP` ＋未解決分）で出せる。容量は500KBに対し通常は余裕があるが、**未解決の放置と1値9KB超（`KEYREADY` / BK索引の肥大）**が先に問題になる。いずれも診断の `ratio` / `valueRatio` で既に監視済み。

### 2.3 実測の取り方（運営者・読取専用、書込みなし）

1. 先に**現在のトリガーとGC実行状況を読取りで確認**。稼働（`ACCESS_ENABLED=true`）のまま使えるのは **`accessAdminStatus`**（管理者のみ・SwitchBot API呼出しなし。ロック取得記録 `HB_ADMIN` / `LOCKFAIL` 以外は書かない）。見る値: `byState`（未解決OP数）、`storage.keys / bytes / ratio / byPrefix`、`heartbeatAt.CLEANUP`（日次GCの最終実行）、`deliveries`、`notifyOutboxPending`、`triggers`（有効なジョブ数）。個別の中身を見ずに件数だけ欲しい場合は `accessAdminInventorySummary`（#857。ON のまま可）。
   - **`accessReadOnlyDiagnostics` は使えない**: `ACCESS_ENABLED` が OFF 以外だと設定確認の段階で停止し、ストアを読まない（本番導入前の診断）。ON の本番では上記の `accessAdminStatus` を使う。OFF の環境（検証GAS等）でのみ `store.valueRatio / ops.unreadable` を含む詳細が得られる。
   - **`unclassifiedKeys`（未分類キー件数）と `valueRatio`（1値9KB比）は、現行の `accessAdminStatus` には出ない**（前者は日次GCの戻り値内のみ、後者は診断のみ）。これを運営者が読取りで得られるようにすることを**前提実装タスク**（§7 #5）とする。実装までは、日次GCが動いていること（`heartbeatAt.CLEANUP`）と `storage.ratio` で代替監視する。
2. 結果は**固定コード・集計値のみ**を #910 に貼る（ID・値は貼らない）。
3. 成長率 = 同じ手順を日次で数日分（`byPrefix` の差分）。未解決OPの増減も記録。

## 4. 推奨アーキテクチャ（案②＋①）

```
 [Script Properties]  ← 正本（現行のまま。LockService/状態遷移/GC は無変更）
        │  PropertiesService.getProperties() を1回読み（一貫したスナップショット。ロック不要・書込みなし）
        ▼
 [accessStateMirrorJob]（新規・独立トリガー。鍵処理の外）
        │  サニタイズ → 固定列のみ → 一括書込み（スナップショット上書き）
        ▼
 [運営者用ミラー Spreadsheet]（Bookings台帳とは別ファイル。閲覧のみ共有）
```

### 4.1 設計原則（必須）

1. **一方向**: シート→Properties の経路を作らない。シートは編集しても何も起きない（読み戻しコードを書かない）。
2. **鍵処理から切り離す**: ミラージョブは `runLocked` の外・別トリガー。失敗しても例外を握り、固定コード `MIRROR_FAILED` と `HB_MIRROR`（最終成功時刻）だけ記録。鍵の発行・削除・配送・GCの成否に影響させない。
3. **サニタイズ**: 出力は固定列のホワイトリスト。暗証番号・`SECRET_`・メール・宛先・本文・完全deviceId・トークンはコード上到達不能にする（診断の `diagSanitize` と同じ方式。値は固定コード/数値/日時のみ）。予約IDの扱い（末尾マスク or 運営者判断で全桁）は §8 で運営者が決める。デフォルトは**末尾マスク**。
4. **スナップショット上書き**: 追記ログにしない。正本から消えた（GCされた）行はシートからも消える＝**保持期間がシート側で延びない**（#690/#887 の保持方針と矛盾しない）。
5. **古さの明示**: 各タブ先頭に「最終更新（JST）」と「N分以上更新が無ければ赤」。ミラー停止を運営者が一目で分かるようにする。
6. **手動編集禁止の表示**: 全タブに「自動生成。編集しても反映されません」を明記し、保護範囲（警告）を設定。**権限の主たる守りは閲覧のみ共有**。
7. **件数ではなく保護状態で判定**: ミラーは `isUnresolved` / 保護済みEVT・BK を正本の判定関数で出す（独自判定を持たない）。

### 4.2 シート構成（案）

| タブ | 主な列（すべてサニタイズ済み） | 運営の使い道 |
| --- | --- | --- |
| `概要` | 最終更新、`ACCESS_ENABLED` の有無、トリガー健全性(`HB_*`)、Properties使用率、未解決OP数、未知キー数 | 稼働の一目確認 |
| `鍵操作(OP)` | OP種別、予約末尾、ブランド、キーパッド末尾4桁、状態、証跡、作成/更新時刻、未解決フラグ、期限 | 未解決・失効・UNKNOWNの確認 |
| `配送(DLV)` | OP参照、配送状態、試行回数、最終試行、要管理者判断 | 暗証番号メールの二重送信/不達の確認 |
| `通知` | 未送達の管理者通知、コード、発生時刻 | 気づかれていない警告 |
| `管理者操作` | 操作種別、日時（90日分） | 監査の目視 |
| `API使用量` | 直近8日の呼出し数、予算比 | 予算の確認 |

### 4.3 書込み方式とスコープ（OAuthゲートを尊重）

現状スコープは `spreadsheets.readonly`。ミラー書込みには書込み可能なスコープが必要で、**新スコープの追加は再承認が要るため、デプロイ検査が `MANIFEST_NEW_OAUTH_SCOPE_REQUIRES_MANUAL_APPROVAL` で止める**（既存のゲートを緩めない）。選択肢:

| 方式 | 追加スコープ | 長所 | 短所 |
| --- | --- | --- | --- |
| **A（推奨）** | `drive.file` | GASが自分で作成したミラーシートだけに書込み可。**Bookings台帳には書けない**（最小権限） | ミラーシートはGAS関数（運営者がエディタで1回実行）で**新規作成**する必要がある。`drive.file` でSheets API `values.update` が通ることを、本番外の検証GASで実機確認してから採用 |
| B | `spreadsheets` | 既存の手作りシートに書ける | 全Spreadsheetへの書込み権限になる（台帳も技術的に書込み可）。コード上のID固定ガード＋テストで補うが、権限は広い |

- どちらも**運営者（デプロイ実行者本人）が、OFFのまま・エディタで再承認**する手順を別Issueで明文化する（既存の `accessCheckSetup` → `accessReadOnlyDiagnostics` の後）。再承認後に**トリガーが有効のままか**を `HB_*` と `ScriptApp.getProjectTriggers` で確認。承認前にマージしても、`appsscript.json` が変わらない限り本番は変わらない。
- 書込みエンドポイントは**ミラーシートID以外を受け付けない**（コード上固定。台帳IDへの書込みは単体テストで失敗させる）。台帳側のSheets APIは引き続き GET のみ。
- 失敗の扱い: 401/403(スコープ/共有)・429(クォータ)・5xx・タイムアウトは固定コードで分類し、次周期に再試行（自動で無限に叩かない。連続失敗は `NOTIFYFAIL` と同様に一定時間後に管理者通知）。

### 4.4 案①（小さな追加）

- 診断/概要に `byPrefix` の増減と `ops.unresolved` の滞留日数を追加し、**キー数ではなく「未解決OPの経過」「1値9KB比」「使用率」**で警告（50件は警告基準にしない）。
- `HB_MIRROR` を `HB_JOBS` に追加（追加し忘れると `unclassifiedKeys` に出る点をテストで固定）。
- 未知接頭辞の件数は現行どおり報告のみ。手動一括削除は作らない。

## 6. 案③を再評価する場合の仕様（参考・今回は実施しない）

**判断条件（いずれも満たした場合のみ別Issueで再評価）**: ②稼働後30日以上で運営の要件がミラーで満たせない（シート上の運営操作が必要）／実測でPropertiesの上限（容量または9KB）が現実的に迫る／運営者が明示承認。

要点（最低限、仕様に含めるべきもの）:

- **ホットパスはPropertiesに残す**（`INBOX_`/`APICOUNT_`/`HB_`/`LOCKFAIL`）。正本移行の対象は `OP/BK/DLV/TRK/ALERT/IALERT/ADMINLOG/KEYREADY` のみ。
- **更新順序の不変条件**: 外部送信(SwitchBot/メール)の**前**に `SENDING` を永続化し、書込み失敗なら**送信しない**（現行の安全側を維持）。外部送信後の結果書込みが失敗した場合は `UNKNOWN`（自動再送しない）。Sheets書込みの失敗率が上がると `UNKNOWN` が増え運営負荷になる点が③の最大のコスト。
- **原子性**: 1遷移=複数行の更新が必要なら1回の `batchUpdate` にまとめる。単一リクエストでの全行適用の保証範囲は実機で検証してから採用する（検証前提）。行の `version` 列で競合を検知（ロックは引き続き `LockService` の単一ロック）。
- **移行手順（OFFにしない）**: P0 実測 → P1 ミラー(②) → P2 **影武者書込み**（正本はProperties、同じ遷移をシートにも書き、差分0を数日確認）→ P3 切替フラグ（`STATE_BACKEND`）を**ロック保持下・未解決OPの引継ぎ検証後**に切替 → P4 旧側を読取専用で一定期間保持（二重書きを継続し、ロールバック可能にする）→ P5 旧側削除（手動一括削除はしない。#887のGCに任せる）。
- **ロールバック**: 切替後も旧Propertiesへの二重書きを維持している間は、フラグを戻すだけで復帰。二重書きを止めた後の復帰は「シート→Properties 逆コピー＋照合」が必要なため、止める前に承認を取る。
- **障害停止と復旧**: シート障害時は `STATE_UNREADABLE` で**新規発行を止め**（fail-closed）、既存キー・既存OPは触らない。復旧後に `accessReadOnlyDiagnostics` → 未解決OPの照合 → 再開。UNKNOWN を自動で解消しない。
