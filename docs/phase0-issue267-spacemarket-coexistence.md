# Phase 0 ゲート確認手順・記録（Issue #267）

対象: Epic #265 / Phase 0 / Issue #267
依存: #266（`gas/booking/` getAvailability。マージ済み）
後続: #267 がPASSするまで #268（createBooking）へ進まない

## この文書の役割

Issue #267 は「スペースマーケットと自社予約システムが、同じ非公開Google Calendarを
予約・空室判定の正として安全に共存できるか」を**実環境で**確認するゲートである。

この確認は実際のスペースマーケット予約・実際のGoogle Calendarへのアクセスを必要とし、
コードレビューだけでは判定できない。そのため本書は以下の2部構成にする。

1. コードレビューだけで確認できる項目（本書内で確認済み。根拠を記載）
2. 実環境でのみ確認できる項目（運用担当者が本書の記録テーブルに実測値を記入し、
   最終的なPASS/FAIL判定を行う）

**本書はテンプレート兼記録簿であり、記入が完了するまで #267 は未PASSのままとする。**

## 1. コードレビューで確認済みの項目

`gas/booking/`（#266）の実装・テストに基づき、以下はコード上ですでに満たされている。

### 1-1. 空き判定はイベントタイトルに依存しない

- `CalendarRepository.gs` の `getBusyIntervalsForDate` は `event.getTitle()` を一切呼ばず、
  `getStartTime()` / `getEndTime()` / `isAllDayEvent()` のみを読む
  （`gas/booking/CalendarRepository.gs:36-47`）。
- `Availability.gs` の `computeBookableStartTimes` もタイトル文字列を一切参照せず、
  占有区間（分単位の開始・終了）だけで判定する（`gas/booking/Availability.gs:104-125`）。
- したがって `[SM]` / `[BLOCK]` / `[WEB]` 等の接頭辞の有無・規約準拠に関わらず、
  Calendar上で時間を占有する予定はすべて占有枠として扱われる。
  → Issue #267「イベントタイトル」節の要件を満たす。

### 1-2. 重複イベントがあっても空き判定が壊れない

- `test/booking-availability.test.js`「重複イベントがあっても誤って空きと判定しない」で
  10:00-12:00 と 11:00-13:00 の重複イベントを与え、正しく13:00+バッファまで
  ブロックされることをテストで固定済み。
- 判定ロジック（`blockedRanges.some(...)`）は各区間を独立に評価するため、
  スペースマーケット予約・自社予約・管理者手入力予定が同時刻に重複しても、
  どれか1件でも占有していればブロックされる（OR条件）。

### 1-3. APIレスポンスにPII・イベント詳細を含めない

- `Availability.gs` の `getAvailability` は `success` / `date` / `durationMinutes` /
  `brand` / `bookableStartTimes` / `error` のみを返す（`gas/booking/Availability.gs:147-153`）。
- `CalendarRepository.gs` はイベントの `startMinutes` / `endMinutes` / `isAllDay`
  以外を一切取り出さない（タイトル・説明・参加者・主催者には触れない）。
- `test/booking-code-runtime.test.js` で `doGet` 配線全体のレスポンス形式を検証済み。
  → Issue #267「Calendarの非公開性」節の
  「`getAvailability` は予約可能時刻だけを返し、既存予定のタイトル・説明・参加者等を返さない」
  を満たす。

### 1-4. 既存Calendarの非公開設定・GitHub Pages側の扱い

- 本Issueでは公開Calendarの新設・分離を行っていない（非対象）。
- `_includes/calendar_embed.html` は #266/#267 のいずれでも変更していない
  （既存の埋め込み設定のまま。埋め込み自体の非公開性は運用側のCalendar共有設定に依存する）。
- 上記のコード確認（1-1〜1-3）により、GAS Web App側からイベント詳細が
  フロントへ渡ることはない。

以上、1-1〜1-4は本書作成時点のコード・テストで再現的に確認できる。
実環境確認（2章）では、これらの保証が**実際のスペースマーケット予約・実際のCalendar**
に対しても成立するかを確認する。

## 3. 日次整合性確認手順（自社予約）

自社予約のbookingId・Spreadsheet台帳は #268（createBooking）で導入されるため、
Phase 0時点では実データによる整合性確認は実施できない。
本書では#268着手後すぐに使える手順のみを先に確定しておく。

**対象は自社予約のみ。スペースマーケット予約はSheets台帳との突合対象にしない
（bookingIdを持たないため）。**

日次（または任意タイミング）で以下を確認する:

1. Calendar上の自社予約イベント（bookingIdをイベント説明またはExtended Propertiesに
   保持する想定。詳細仕様は#268で確定）が、Spreadsheet台帳に同じbookingIdで存在するか
2. Spreadsheet台帳のCONFIRMED/PENDING行それぞれについて、対応するCalendarイベントが
   存在するか
3. 一致しない場合（片方にしか存在しない）は recovery 記録に残し、手動調査する

この手順は#268でbookingId発行・Calendar/Sheets書き込みが実装され次第、
実データで運用を開始する。

## 4. PASS / FAIL判定

Issue #267 記載のFail条件のいずれかに該当する場合はFAILとする。

- スペースマーケット予約が同じCalendarへ反映されない
- 反映遅延が大きく、自社予約との競合リスクを許容できない
- 連携が不安定

上記のいずれにも該当せず、2章の実環境確認がすべて期待通りであればPASSとする。

**判定: PASS（2026-09-19実施）**

根拠:
- 過去のCalendar履歴上、スペースマーケット予約（少なくとも7件）はすべて同一の
  自動生成フォーマットで同じCalendarへ反映されており、反映は安定している
- 反映遅延は実測1件で数秒未満。残り2件は同一自動連携パターンからの推定であり、
  実測ではないが、いずれも実運用上問題ないレベルと判断できる
- 実デプロイ済み `getAvailability` は、スペースマーケット予約2件（同日の連続予約含む）・
  DM経由の管理者手入力予定1件のいずれについても、対象スロットを漏れなく
  `bookableStartTimes` から除外した（2-3）
- 重複イベント（実環境でのテスト予定二重作成）でも誤って空きを返さないことを確認した（2-5）
- `getAvailability` のAPIレスポンス・既存の `calendar_embed.html` のいずれからも
  イベントタイトル・参加者等のPIIは露出しなかった（2-6）

未実施項目（2-7: SNB/mens/Studio Xの3ブランド実地相互比較）はコードレビューで
判定ロジックのbrand非依存性を確認済みのため、PASS判定を妨げる要因としない。

判定確定後、この行を更新し、Issue #267のコメントまたは本文にも
PASS/FAILを明記すること（受入条件）。FAILの場合、フォールバック方針
（手動ブロック運用 / 転記SLA / 連携方式見直し）は別Issueで決定し、
#268には着手しない。
