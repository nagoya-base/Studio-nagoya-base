本文は、実装（`gas/booking/README.md` Issue #680節）と一致させている。**本文とお知らせは、効力発生日が自動消去の開始日ではなく、日次処理は準備が整い開始条件を満たした後に開始することを明記している**（3言語・全ブランド版。本文だけを先に公開する期間も、利用者に稼働中の処理と誤認させない）。書いていないこと: 「すべての情報が180日で消える」「匿名化済み」（台帳には照合可能なIDが残る。本文に「匿名化された情報ではありません」と明記）、540日・稼働済みの表現（540日後の限定記録消去は現コードでは未実装）。「この運用の開始前に保存期間を過ぎていた情報も、開始後の処理により順次消去する」と書くことで、効力発生日と自動消去の実際の開始日が離れていても、本文が事実と合う。

### マージ（公開）してよい条件 — すべて満たすまで Draft のまま
1. 第1段階の予告が、**全版（SNB・SNB mens・英語・Studio X・お知らせ）で実際に公開され、表示を確認できている**。確認できた日を「告知日」として記録する。
2. **効力発生日 ≥ 告知日 + 14日**（現行ポリシー11項）。1つでも公開確認が遅れた版があれば、その確認日から数え直す。
3. マージの日が効力発生日以降である（効力発生日より前に本文を公開しない）。

### 日付がずれたとき（バックデートしない。原予告を書き換えない）
**原予告（2026年11月1日付。「2026年11月15日に改定」）は履歴として残し、本文も日付も変えない。** 延期するときは、原予告を直さずに**訂正／延期の告知を追加**する。

1. `_data/news_ja.yml` の先頭に、**実際に公開する日付で**、`【訂正】`または`【延期】`で始まる告知を追加する。当初の予定日（2026年11月15日）、新しい効力発生日、原予告の告知日（2026年11月1日）を書く。
2. **新しい効力発生日 ≥ 訂正告知の公開確認日 + 14日**（短縮はしない。当初の予定日より早めることもしない）。
3. 新しい効力発生日に合わせて直す（原予告以外）: `_data/news_ja.yml` の「改定のお知らせ」の日付と本文中の日付、`_includes/legal_ja.html` の最終改定日、`studio-x/legal/index.html` の履歴の日付、`docs/` の日付。
4. `test/privacy-retention-notice-690.test.js` の `EFFECTIVE` / `EFFECTIVE_JA` だけを新しい効力発生日に直す。`ORIGINAL_NOTICE_DATE` / `ORIGINAL_PLANNED` / `ORIGINAL_PLANNED_JA` は変えない（テストが、訂正告知の存在と日付を検査する）。

### 公開後
本番開始（有効化）は別の条件（#690）。本文の公開は自動消去の開始を意味しない。自動消去を開始した後は、必要なら「開始前に保存期間を過ぎていた情報も…順次消去する」の一文を見直す。

### 書かないこと
- 「すべての情報が180日で消える」「匿名化済み」（台帳には照合可能なIDが残る。README明記）。
- 「540日で必ず消える」「稼働済み」。540日保持は運営方針として採用済みだが、**540日後の限定記録の消去は現コードでは未実装**。第2段階の文面で期間の数字を載せるかは、後続実装との整合をレビューで確定する（本PRのお知らせは数字を載せない）。
- 実ファイルURL・ID・顧客情報・予約ID・決済ID・メール本文。
